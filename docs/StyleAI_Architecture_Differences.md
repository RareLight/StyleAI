# StyleAI vs LrGeniusAI: Architecture & Implementation Differences

This document summarizes the extensive architectural changes, model upgrades, and new features introduced in **StyleAI** compared to the original **LrGeniusAI** repository. Our goal with this fork was to narrow the scope toward a highly-performant, privacy-centric, and highly personalized AI photography assistant that learns directly from a user's unique editing style.

## 1. Vision Model Upgrade: OpenCLIP to SigLIP2

We completely replaced the legacy OpenCLIP model with Google's **SigLIP2** (`ViT-SO400M-16-SigLIP2-384`).

* **Reasoning**: SigLIP2 utilizes a sigmoid loss for image-text pairing rather than standard softmax contrastive loss. This allows it to perform much better at dense image understanding and zero-shot classification across diverse photographic styles, lighting conditions, and subject matter.
* **Implementation**: The backend Python server downloads and caches the SigLIP2 weights on demand. The 1152-dimensional embeddings generated by SigLIP2 are stored in **ChromaDB** and provide the foundation for our semantic search, duplicate detection, and our new Style extraction algorithms.

## 2. Advanced Style Detection & AI Editing

The most significant divergence is our shift toward personalized AI editing recipes. LrGeniusAI focused on generic AI generation; StyleAI focuses on learning the photographer's specific visual style.

* **Style Catalog & Training Pipeline**: We introduced a completely new workflow (`TaskTrainFromEdits.lua`) that allows users to save specific photos as "AI Training Examples." 
* **The Mechanism**: 
  1. When a user trains an image, we extract its final Lightroom Develop settings (the "recipe").
  2. We pass the image through SigLIP2 to generate a visual embedding, and through an LLM (Gemini/ChatGPT/Local) to generate a dense semantic caption of the scene's lighting and composition.
  3. When the user selects "AI Edit Photos", the system queries ChromaDB to find the closest visually and semantically matching training example.
  4. An LLM dynamically interpolates the develop settings from the training example to perfectly fit the target photo's exposure and contrast requirements.
* **Reasoning**: Professional photographers don't want generic "auto-edits". They want an AI that replicates *their* specific grading style for a specific lighting scenario (e.g., "Golden Hour Portrait" vs "Harsh Midday Sports").

## 3. Asynchronous Pipelining & Performance (The `perf-optimize` branch)

We completely overhauled the Python backend's ingestion and indexing pipeline to eliminate UI blocking and maximize hardware utilization.

* **Reasoning**: The original implementation processed images sequentially, meaning the GPU sat idle while the CPU decoded the JPEG, and the CPU sat idle while the GPU ran the embedding model.
* **Implementation**: We introduced a `ThreadPoolExecutor` architecture. The CPU handles JPEG decoding, hashing, and face-detection preprocessing on background threads, while feeding a thread-safe queue to the GPU (or Neural Engine on Mac) strictly for SigLIP2 and InsightFace inference. This asynchronous pipelining resulted in massive speedups during bulk catalog indexing.

## 4. Robust State & Lifecycle Management

We recognized that running a local Python server alongside a Lightroom Lua plugin requires extremely robust state management to prevent zombie processes and data corruption.

* **Lifecycle Controller**: We implemented `server_lifecycle.py` which uses PID tracking and `.OK` heartbeat files to ensure the Python backend starts reliably, unloads large models from VRAM after 30 minutes of inactivity, and dies cleanly when Lightroom closes.
* **Catalog Isolation**: Instead of a single monolithic database, we implemented "soft-state" catalog scoping. Photos in ChromaDB include a `catalog_ids` metadata list. This allows a single backend to serve multiple Lightroom `.lrcat` files without cross-contaminating search results.
* **1:1 Lossless State**: We implemented a `POST /db/prune` endpoint that allows Lightroom to send a master list of active `globalPhotoId`s to the backend, cleanly purging orphaned embeddings from ChromaDB without requiring the server to parse the proprietary `.lrcat` SQLite file directly.

## 5. UI Polishing & Asynchronous UX

* **Yielding `pcall`**: We replaced native Lua `pcall`s with `LrTasks.pcall` throughout the codebase, allowing long-running operations (like network requests to the backend) to yield properly without locking the Lightroom UI thread.
* **Real-time Status**: Complex operations, such as the ~4GB SigLIP2 model download, now actively poll the backend via `/clip/download/status` and update the Lightroom Onboarding Wizard UI with real-time progress, ensuring the user is never left wondering if the plugin has stalled.
